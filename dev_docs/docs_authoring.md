# 製品ドキュメントの執筆・検証

文書の読者・責務・配置は [文書配置ルール](README.md#ドキュメント配置ルール正本) に従う。
本書は `docs/` を執筆・確認する際の詳細な規約と手順の正本とする。
資料と比較の扱いは [共通の記載ルール](README.md#資料と比較の記載ルール正本) に従う。

## 本文

`docs/` はGUIから利用する構造設計者向けに、設計・検討の判断に必要な情報を説明する。
外部AIの通信仕様と保存形式の専用節では、外部連携に必要な要求・応答・形式の契約も扱う。

- 採用する理論・計算モデル、式・算定方法・仮定
- 入力値の意味・適用範囲、既定値と根拠
- 制約・非対応事項、結果の意味・読み方・設計上の注意事項
- 必要な法令・告示・規準の特定情報、GUI の現在仕様・操作上必要な情報

計算上の方式に有用な違いがある場合は、方式ごとの考え方と SEPIKA が採用する方式・適用条件を説明する。
方式を無理に列挙せず、実際に採用する式・記号・数値・入力条件・制約と結果の読み方を示す。
原典や文献の紹介だけの記述、他の構造解析・構造設計ソフトの資料による説明や紹介・照合の履歴は本文に書かない。

本文・表は GUI 上の名称、入力、選択肢、制約、計算理論、結果の意味で説明する。
Rustの型名・enum・フィールド・内部ID・実装処理をGUIの説明へ混在させない。
通信・保存形式の専用節では、外部の呼出側が使用するフィールド名・型・失敗条件を明記する。
Rust APIの契約はRustdocを正本とし、呼出手順やコードから読める処理説明を本文へ複製しない。
GUI から見えない処理順序・データ構造、実装上の回避策、リファクタリングや旧実装との差分は、
コード・ADR・handoff に置く。

### 説明の分量と構造

- 操作、入力の選択、適用可否、結果の解釈、計算根拠の理解に必要な説明を残す。説明量を完成度の基準にせず、表・式の言い換えや判断に役立たない補足・例示は省く。
- 重複する説明は正本の節へまとめ、他の箇所は要点と直接リンクにする。ただし、操作前に必要な条件・警告はその場にも残す。
- 長いページ・節は「目的→採用する考え方・通常の使い方・重要条件→詳細・根拠・例外」の順で構成する。方式名や参照先の列挙だけを概要にせず、モデルが何を表すか、入力から何を求めどの判断へ進むかを説明する。操作・保存・外部連携では通常の手順と操作後の状態を先に示し、適用可否や安全な利用を左右する条件は操作前にも残す。
- 章の入口は目的に応じたページへの案内とし、短い一覧や既に明確なページへ形式統一のための概要を追加しない。
- 要点を先に置き、一段落は一つの論点にする。順序は番号付きリスト、並列条件は箇条書き、比較は表で示し、条件のAND／OR関係と例外の適用先を保つ。
- 長文を巨大なリスト項目・表セルへ移すだけにせず、説明自体の統合・短縮も検討する。見出しやリストを過剰に細分化しない。
- 短縮後も数式・数値・単位・既定値、適用条件・例外・警告・未確認事項・出典、公開仕様を保持し、結果と次の操作が対応するか確認する。

### 数式と計算根拠

計算の説明は、次の順に読めるように構成する。既に説明した記号や条件は、該当節への参照でよい。

1. 計算の目的：何を求め、どの判断に使うか。
2. 仮定・適用条件：モデル化、近似、対象範囲と適用できない条件。
3. 記号・単位：入力と未知量の意味、単位、符号・座標の取り決め。
4. 採用式と必要な中間量：入力から結果までを追うために必要な式と、そのつながり。
5. 結果の意味：出力の単位・符号、判定方法、解釈上の制約。

- 単独の記号や短い式の参照はインライン式にする。
- 主要な算定式は独立式にする。分数・総和・積分、場合分け、行列、複数段階の変形は、
  文中で読みづらくなる場合に独立式へ分け、必要な中間量を順に示す。
- 表は記号・単位・適用条件の整理に使う。長い式や計算手順をセルへ詰め込まず、表から本文の式へつなぐ。

次は記載方法の例であり、製品の適用範囲を定めるものではない。

**改善前**：式と前提を表のセルにまとめている。

| 計算 | 内容 |
| --- | --- |
| 一様な棒の伸び | 線形弾性の微小変形で一定の引張軸力に対し \\( \delta = \varepsilon L = \frac{\sigma L}{E} = \frac{NL}{EA} \\)。単位は mm。 |

**改善後**：目的・条件、記号の表、独立式、結果の意味をつなぐ。

一様な棒の軸方向の伸びを求める。線形弾性・微小変形を仮定し、材軸方向に一定の引張軸力が作用する場合を扱う。

| 記号 | 意味 | 単位・条件 |
| --- | --- | --- |
| \\( N \\) | 引張軸力 | N、正を引張とする |
| \\( L \\) | 棒の長さ | mm、正 |
| \\( E \\) | ヤング係数 | N/mm²、正・一定 |
| \\( A \\) | 断面積 | mm²、正・一定 |
| \\( \sigma, \varepsilon, \delta \\) | 軸応力度、軸ひずみ、軸方向の伸び | 順に N/mm²、無次元、mm |

表の入力から軸応力度、軸ひずみ、伸びを順に求める。

\\[ \sigma = \frac{N}{A}, \qquad \varepsilon = \frac{\sigma}{E} \\]

\\[ \delta = \varepsilon L = \frac{NL}{EA} \\]

得られた \\( \delta \\) は棒全長の伸び（mm）であり、正の値が伸長を表す。

標準的な理論式は、仮定から採用式につながる必要な導出や、実装と独立した手計算例で根拠を補う。
経験式・規準式は無理に理論的に導出せず、出典名・版・式番号（式番号がなければ節・ページ等の特定位置）、
係数・単位・適用条件を示す。原典で照合済みの範囲と未照合の範囲を区別し、未照合部分を確認済みと扱わない。
照合の履歴・証跡は既存の配置ルールに従い、本文には採用式の根拠と確認範囲を記す。
コードとの一致だけを数式の妥当性の根拠にしない。コードへの導線は、次の「実装参照」に従って別欄に置く。

## 実装参照

説明した理論・仕様に対応する SEPIKA 自身のコードへの独立した導線を、本文・表から分離した既存の共通表示で示す。

```html
<div class="impl-ref">

**実装参照**：`sepika_xxx::module::item`（`crates/...`）が実装します。

</div>
```

- 参照先はコードを検索して実在を確認する。private / `pub(crate)` の実装位置も示してよい。
- 行番号を使わず、モジュール・関数・型・ファイル等の安定した入口を示す。
- 入口は必要最小限（目安 1〜2 個）とし、独立した役割が複数ある場合は必要に応じて増やす。
- 説明節の直後や節末に置く。既に参照がある場合は重複させない。
- ページ末尾の `## 実装参照` にまとめる既存方式も維持し、節ごとの参照と二重に管理しない。
- 実装の詳細や設計経緯は展開せず、コード・ADR・handoff 等を正本とする。

## ページ構成

- ページを追加・削除したら [SUMMARY.md](../docs/SUMMARY.md) と章の README の一覧を更新する。
- 章は章ディレクトリと小項目ページで構成する。
- 章・節番号は mdBook が自動採番するため、SUMMARY のタイトルやページ見出しに番号を手書きしない。
  本文の節参照には、番号ではなく見出しタイトルへのリンクを使う。
- 数式は MathJax 用の `\\(...\\)` / `\\[...\\]` で記述する。
- 章の追加や表示・フッターを変更する場合は [book.toml](../docs/book.toml)、
  [実装参照の表示](../docs/theme/impl-ref.css)、[footer.js](../docs/theme/footer.js) と
  [footer.css](../docs/theme/footer.css) の設定・実装を確認する。redirect やアンカーの取り決めはこれらを正とする。
- 公開・API リファレンス生成の処理は [docs workflow](../.github/workflows/docs.yml) を正とする。

## ローカルでの確認

[mdBook](https://rust-lang.github.io/mdBook/) が必要。未導入の場合は `cargo install mdbook` で導入する。
リポジトリルートで以下を実行する。

```bash
# リンク切れと実装参照パスの実在を確認する
cargo run -p xtask -- check-docs

# 静的 HTML のビルド
mdbook build docs

# プレビュー（変更を自動リロード）
mdbook serve docs --open
```

`check-docs` はビルド時のリポジトリルートにある `docs/` を検査する。ルートまたは `docs/` が
存在しない、ディレクトリではない、読み取れない場合は、対象パスと理由を示して失敗する。
開発者向け文書を変更した場合は、変更した文書の
リンク先・見出しアンカーも確認する。

数式を変更した場合は、Markdown 原文だけでなく生成 HTML 内の MathJax 入力とブラウザ表示を確認する。
不等号の向き、場合分け・行列の行区切りと括弧、添字、空白記法が原文の意図を保っているかを確認する。
特に `\,` がカンマへ変わる、`cases` の改行や集合括弧が消える、数式内に意図しない `em` / `strong` タグが
混入するといった Markdown 変換による崩れを確認する。必要なエスケープは生成 HTML を見て調整する。
ビルド成功や HTML の静的確認だけでは、MathJax による組版・はみ出し・改行の見やすさまでは確認できない。
