## 調査時点と再現入力

調査基点: `db1282251aadf585cb7b52e585df68164305527b`、ブランチ `investigate/684-story-application-lifecycle`。Windows PowerShell、`rustc 1.99.1 (58cf8f9c3 2026-10-13)`、`cargo 1.99.1 (5f94df478 2026-08-27)`。`CARGO_TARGET_DIR` / `RUSTFLAGS` / `RUST_BACKTRACE` は未設定だった。

1. `sepika_app::sample::portal_frame` の構造節点4個を入力とし、公開 `generate_stories_with_opts(model, &[], true, CorrectedLumped)` と既存 `apply_generated_weights` で2階・6節点・代表節点4/5・生成記録付きモデルを作った。重量の計算手順をprobeへ再実装していない。
2. 手入力対照では第2階の重量overrideと採用重量を123456 N、Ciを0.42、代表節点拘束をFIXEDへ変更し、記録のinput/output keyをそれぞれ `[255]` / `[254]` にした。参照IDは変更しない。
3. 階削減用結果は別cloneへ `UndoStack.run(DeleteStory { story: StoryId(1) })` を行い、参照検査とOVIKA保存が正常な1階モデルから公開生成器で作った。その結果を元2階モデルへ旧APIで採用した。
4. 現用対照は生成済みcloneを `ApplyPreparedModel` で採用した。また `App::default` → `load_model(portal_frame)` → 公開 `generate_stories_action` を直接呼び、同じAppの公開UndoStackで履歴を操作した。privateなGUI Undo/Redoアクションやnative GUI手操作ではない。

比較は `Model::eq_ignoring_dofmap` による期待Modelとの一致、生成記録の一致、`validate_reference_ids`、`weights_are_current`、実 `save_ovika` / `load_ovika` で行った。正常保存では読込Modelのnamed MessagePack bytesが保存前と一致すること、不正保存では事前に置いた既存ファイルbytesが保持されることをassertした。各観測で入力Modelの同bytes不変も確認した。数値解の許容差による合否判定ではない。

## 呼出所有の調査

基点のRustソース全体を旧API名で検索した。実構築は `sepika-edit/src/tests.rs` の2試験、`sepika-app/tests/source_story.rs` のhelper、ignored `sepika-app/tests/perf_probe.rs` だった。`RestoreStories` は `load_case.rs` 内の逆操作生成に限られた。Appソース中の3記述はコメントであり実呼出ではない。
現用production経路は `sepika-app/src/app/actions/loads.rs` のclone → `sepika_job::prepare::prepare_model` → `ApplyPreparedModel`。外部利用者の有無をこの検索から結論しない。

旧APIの階削減不正では、生成記録だけを除いたcloneの参照検査は成功した。拒否原因は現用階・節点・拘束ではなく残存した旧記録のtyped参照だった。保存拒否で既存ファイルと入力Modelが保持された。保存時拒否は旧APIの正常性を証明しない。
同階の正常staleと、不在参照による不正を区別した。実Appの初回生成は自動荷重準備も含むため、密度直接算入probeの重量値との同一条件比較はしていない。
